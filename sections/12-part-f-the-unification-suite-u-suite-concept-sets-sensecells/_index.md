# Part F — The Unification Suite (U-Suite): Concept-Sets, SenseCells & Contextual Role Assignment

- [F.0.1 - Contextual Lexicon Principles (F.0.1)](01-f01-f01-contextual-lexicon-principles.md) — Establishes the rule that every word must be pinned to a specific local context; crossing into another context requires an explicit, declared translation.
- [F.1 - Domain‑Family Landscape Survey (F.1)](02-f1-f1-domainfamily-landscape-survey.md) — Helps teams map which authoritative sources actually define terms in a field before anyone starts naming or comparing things.
- [F.2 — Term Harvesting & Normalisation (F.2)](03-f2-f2-term-harvesting-normalisation.md) — Shows how to collect and stabilise the actual words a discipline uses, without mixing up senses from different fields.
- [F.3 - Intra‑Context Sense Clustering (F.3)](04-f3-f3-intracontext-sense-clustering.md) — Groups harvested terms by what they actually mean inside one field so you don't treat superficial variants as different things.
- [F.4 - Role Description - Description Episteme for U.Role (F.4)](05-f4-f4-role-description-description-episteme-for-urole.md) — Provides a compact, reusable card that makes a work-facing role recognisable and checkable without letting it absorb unrelated claims.
- [F.5 - Naming Discipline for U-kind Names and RoleDescription Labels (F.5)](06-f5-f5-naming-discipline-for-u-kind-names-and-roledescription-la.md) — Keeps names honest by requiring each label to reflect only the meaning it was recovered from, not an entire imported tradition.
- [F.6 - RoleAssignment and Performed-Work Attribution Check (F.6)](07-f6-f6-roleassignment-and-performed-work-attribution-check.md) — Decides whether work can legitimately be attributed to a specific person or system through a declared role in a specific context and time window.
- [F.7 - Concept‑Set Table (F.7)](08-f7-f7-conceptset-table.md) — Displays, in one table, which terms from different fields are licensed to be treated as equivalent and exactly where that equivalence breaks down.
- [F.8 - Mint-or-Reuse Decision (F.8)](09-f8-f8-mint-or-reuse-decision.md) — Prevents vocabulary sprawl by forcing a deliberate choice: reuse an existing name, assign a local label, or justify why a brand-new durable name is actually needed.
- [F.9 - Alignment and Bridge across Contexts (F.9)](10-f9-f9-alignment-and-bridge-across-contexts.md) — Lets teams formally translate a term from one field to another while stating exactly what meaning is lost in the translation.
- [F.9.1 - Bridge Stance Overlay (F.9.1)](11-f91-f91-bridge-stance-overlay.md) — Adds a compact interpretive label ("rough analogy", "projection", "local rename") on top of an existing translation card without widening what the translation permits.
- [F.10 - Status Families Mapping: Evidence, Standard, and Requirement Status (F.10)](12-f10-f10-status-families-mapping-evidence-standard-and-requiremen.md) — Untangles overloaded status words like "validated" by requiring each claim to state which type of status it is and what exactly it applies to.
- [F.11 - Method Quartet Harmonisation (F.11)](13-f11-f11-method-quartet-harmonisation.md) — Keeps the abstract way of doing something, the written recipe, the actual run, and the control signal in separate categories so none can masquerade as another.
- [F.12 — Service Acceptance–Work Evidence Link (F.12)](14-f12-f12-service-acceptancework-evidence-link.md) — Ties a service promise to actual recorded events, preventing a plan or control signal from being counted as proof of delivery.
- [F.13 - Lexical Continuity & Deprecation (F.13)](15-f13-f13-lexical-continuity-deprecation.md) — Governs how to rename, alias, or retire a term so readers can always trace what the old label meant and why it changed.
- [F.14 - Anti-Explosion Control for Role and Status Name Families (F.14)](16-f14-f14-anti-explosion-control-for-role-and-status-name-families.md) — Stops role and status vocabularies from growing unchecked by requiring each new name candidate to be justified against existing alternatives.
- [F.15 - Static and Regression Conformance Harness for Unification (F.15)](17-f15-f15-static-and-regression-conformance-harness-for-unificatio.md) — Checks whether a set of terms, roles, and bridges is locally sound right now and stays sound as any part of it changes over time.
- [F.16 - Worked‑Example Template (Cross‑Domain) (F.16)](18-f16-f16-workedexample-template-crossdomain.md) — Provides a page template for cross-field examples that forces every term to carry its local context and every translation to state its losses.
- [F.17 - Unified Term Sheet (F.17)](19-f17-f17-unified-term-sheet.md) — Publishes a compact, reader-facing table of reviewed term decisions so teams can reuse stable names without redoing the entire unification argument.
- [F.18 - Local-First Unification Naming Protocol (F.18)](20-f18-f18-local-first-unification-naming-protocol.md) — Governs how a locally useful expression graduates into a stable, reusable name without accidentally creating a hidden second vocabulary system.
- [F.19 - Ontology-First Plain Technical Rewriting (F.19)](21-f19-f19-ontology-first-plain-technical-rewriting.md) — Repairs technical prose by stripping away structural scaffolding so the actual object and claim become visible before any wording is adjusted.
